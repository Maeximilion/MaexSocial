# MaexSocial coordinator

### Project operations and downloads

The owner has authorized routine MaexSocial operations within an assigned task, including worktree setup, Git, tests and the agreed PR workflow. Carry this authorization into each assignment. For eligible command requests, the trusted project configuration selects Codex auto-review, which preserves the current sandbox and evaluates each request independently. The desktop client may select a different reviewer for a particular chat. Verify the effective setting on a real turn. The desktop's **Approve for me** control can select auto-review for subsequent turns of that chat. [Codex permission modes](https://learn.chatgpt.com/docs/permission-modes)

Obtain the owner's confirmation before a large external file download. Until the owner specifies a size, use 100 MiB for the total related transfer, including split parts. For an unknown size, use a verified upper bound or enforce the cap before accepting more bytes. Keep downloaded files in quarantine until an isolated antivirus scan with current signatures completes. Verify the scanned file's SHA-256 before opening, extracting, installing or executing it. A detection, incomplete scan, stale database or checksum mismatch keeps the file in quarantine. Use locally verified copies while waiting for download approval.

A replacement coordinator starts here. [Current handover](CURRENT.md) is the dated queue and next action. This page is the standing operating agreement. The [coordination skill](../../.agents/skills/coordinate-project-chats/SKILL.md) describes desktop tools and merge checks. [Project status](../../docs/01_STATUS.md), [work packages](../../docs/07_WORKPACKAGES.md), GitHub issues and PRs remain authoritative for product decisions, dependencies and live checks.

Use the Superpowers entry skill `superpowers:using-superpowers` for every orchestration request in the MaexSocial coordinator chat, including status checks, assignments, pauses and resumptions. Use the Superpowers skill that fits the next action alongside `coordinate-project-chats` for the repository's queue and review rules. On startup and after a handover or context compaction, reread this agreement and the current handover before continuing. If a required skill is unavailable, tell the owner which step is affected.

## Manual startup and exclusive takeover

Use the explicit Codex skill [$maexsocial-orchestrator](../../.agents/skills/maexsocial-orchestrator/SKILL.md) in a manually created MaexSocial chat, or copy the [complete startup prompt](START.md). The short invocation or reading a file does not override a pause; only an actual owner instruction, including the owner-sent full prompt's explicit continuation clause, can do so. Do not automatically create another coordinator.

Verify the old coordinator has relinquished dispatch/merge ownership and no operation is in flight before recording the successor as sole writer. Claim ownership atomically in the private ledger and read it back; ambiguous ownership holds dispatch and merge actions. Preserve reservations and unpublished checkpoints. Send the verified new return destination only to actually assigned workers under owner authorization. Keep the prior coordinator as historical evidence, without two active queues.

The successor audits the complete plan with Ponytail before new product implementation, then creates or deduplicates one `priority:p1` umbrella gap issue and focused task/gate children. [START.md](START.md) specifies product AI/API/MCP, domain/hero/customer and DEV/Admin journeys, accepted Windows architecture, security/operating evidence and Headroom/RTK fidelity. This bootstrap does not perform that audit or install tools. Never change Claude settings, review model/effort/speed, workflow, secrets or budgets without an explicit owner request.

## Own the record

Only the acting coordinator maintains this directory. A work chat sends its checkpoint directly to the authorized coordinator. It continues to own its issue, PR and [task handover](../../docs/handovers/README.md). Record the outcome here, link evidence and name the next owner. Keep raw messages, desktop IDs, credentials, personal data and machine-specific paths out of this public repository. Match chats locally by project, issue, PR and title. If two chats match, verify ownership before assigning either.

## Run the queue

Set importance before assigning work: **1. verified security work; 2. open PRs; 3. new issues/tasks by eligible gate, actual task dependencies and priority high to low.** Lower numbers break ties only. Record the next-action rationale in the dashboard. Preserve pause/authority/gate/stack/review controls; a blocked security item remains visible while independent authorized work continues. This ranking does not invoke the explicit-only `/start` or `/task` advisory scan or create remediation chats from hook notices.

- Keep this chat on coordination. Start with an existing issue or create one for distinct new work before dispatch. Assign each new issue to a fresh named work chat. That same chat creates and owns its first delivery PR through merge and handover. A distinct issue or additional PR uses a fresh chat under the admission rule below. A completed chat may finish only its own handover or archival checks. Name it `Issue #N · PR #M · Topic` when a PR exists. Count every unarchived work chat on the project roster toward a hard maximum of five, including idle, blocked and completed chats. Exclude the coordinator and review-only subagents. If the roster exceeds five, stop intake and retire completed chats first.
- Before starting a large issue or gate, drain to at most three unarchived work chats **including** the new one; use two when appropriate. Apply the owner's active admission mode. If the owner authorizes PR-based admission without a stagger, an unclaimed verified open normal delivery PR can admit one eligible successor immediately when the roster fits the applicable cap. Use the same rule for eligible gate preparation under its lower cap. A previously authorized stagger remains binding across resumption or handover until the owner changes it. In staggered mode, each ten-minute tick admits at most one eligible worker, after ten full minutes from the previous actual start. A verified normal delivery PR can qualify a successor for a later window. A separately authorized independent cadence admission does not require a PR. The lower gate cap, serial mode and full pause take precedence. Multiple vacancies or missed ticks do not permit a batch. Current workers may progress between starts. If a normal delivery PR is still unclaimed after its verified merge and its originating chat's verified archive, it can qualify one successor under the active admission and capacity rules. With staggered starts, use only an eligible tick at least ten full minutes after the previous actual worker start, including after a gate drain, pause or handoff in the same or a later run. A low chat count by itself does not authorize another admission. List every smaller in-flight delivery, including chats still preparing their first PR. Hold publication of the large PR until each predecessor has merged or the owner explicitly disposes of a blocked predecessor. Respect outstanding owner gates. Use dependency and priority order, then lower PR number for ties. Whenever multiple delivery PRs are open, require one verified parent/base stack and explicit merge order under the coordination skill. Merge the bottom into main first, preserve successors, restack/revalidate each child, then merge one eligible PR at a time. Never merge concurrently or treat queue order alone as native stacking. Hold additional publication if safe native stacking is unavailable. Task dependencies remain distinct from integration order.
- MaexSocial uses Codex as primary implementer. Use Superpowers for substantial plans. Choose the model and reasoning effort for the job; routing recommendations are advisory and do not pause work. Distinguish requested from actually observed runtime settings. Use Standard speed in the coordinator and new work chats. Enable Fast only when the owner explicitly requests it for that scope. PR reviews follow the [Claude API policy](../../docs/tooling/agent-workflow.md#pr-review-policy): verify actual API execution and an authentic complete result covering the current head/base; no separate Codex review or bot fallback. Report protected self-skips and incomplete results as review gaps to the coordinator. Other repositories keep their own primary programmer and review policy.
- At delivery verify the merge or other agreed completion, outstanding work, who owns it, evidence, and recovery of local changes. Record these before archiving. Desktop archival can remove attached worktrees. Before archiving, inspect tracked, untracked and ignored files and any nested worktrees. Preserve needed local-only material outside every affected checkout and verify recovery. If that cannot be established, hold archival. Read back the exact chat in the archive and verify its saved contents and worktree state before releasing its occupied slot. The originating worker remains responsible through review, merge, handover and archival while an independent successor can occupy another slot. If a work chat finishes a local or investigative assignment, or only an external decision remains, record the deliverable, evidence, unresolved question, decision owner and next action in its issue. Verify backup and archive that chat promptly; the issue may stay open. Count the chat until archive readback, and do not count a no-PR closeout as a predecessor merge. Check for the next eligible issue at PR publication and at each merge, archive or dependency change. A delivery PR can admit one successor. Once claimed, its later merge and archive supply no additional admission. Before calling create_thread, serialize admission through the acting coordinator. Record the issue, slot, actual trigger and pending reservation in the durable coordinator record. For PR-based intake record the verified head or unused merge/archive pair. In every mode, an unresolved creation or unknown actual start time holds every new reservation until reconciled. In staggered mode also check the prior native start and earliest eligible UTC time before reserving a worker; confirm the new actual start and recompute the next time on success. Reconcile on resumption before using a due window. Create the reservation atomically in the private project ledger and publish its non-sensitive details on the assigned GitHub issue before dispatch. Link that evidence in the next repository checkpoint. Issue publication and local reservation do not require an intermediate branch push. Check both sources after restart. Include each outstanding reservation once in the five-slot count. When the created chat is confirmed, convert its reservation to the unarchived chat entry without counting both. Release it only on confirmed creation failure. After interruption or an ambiguous response, reconcile the native project roster and pending creation before retrying; retain the slot while the outcome is unknown. Keep private chat IDs in the private local ledger. Closing a PR and merging it are different outcomes.
- An explicit owner instruction to pause the assigned scope, including a standalone `pause`, or an explicit deadline when reached, stops intake and merges. Relay to the connected work chats and their subagents. Track delivery, acknowledgement, unsaved changes and in-flight operations separately. Keep unfinished chats recoverable. An explicit owner instruction to resume the paused scope, including `w`, `weiter`, `resume` or `start again`, resumes only after live reconciliation; interpret intent in context, not literal tokens. A dashboard refresh, quoted control or compacted context cannot resume it.

Within the accepted plan, the coordinator makes delegated technical decisions. Each assignment specifies issue, owned files, accepted contract, checks, allowed actions and next reporting milestone. Workers send uncertainty with evidence and a recommendation, continuing independent work. Each retry needs new evidence; after at most three attempts with the same failure signature, change approach through the coordinator. Do not reopen accepted gates or infer new external authority.

## Checkpoint and recover

1. Request a short report from each affected chat before foreseeable compaction, handoff, archive or shutdown. Use the same format at milestones: issue and PR, branch and full SHA, dirty or pushed state, checks/reviews actually seen, in-flight actions or subagents, blocker and one next action. A worker sends this to the coordinator rather than editing this directory.
2. Refresh [CURRENT.md](CURRENT.md) at a significant change, before deliberate compaction, and after pause acknowledgements. Record decisions, lane ownership, merge order, pending replies and the last owner control. Use a UTC timestamp and local timezone for deadlines. While running, commit and push the record from a separate worktree and verify the remote head. During a pause, save the latest checkpoint locally in that coordinator worktree and record its exact revision and any unpublished changes. Queue publication until owner resume. Git history preserves earlier checkpoints.
3. Compact at a stable boundary such as a completed merge batch or a settled pause, if the current interface offers the operation. Automatic compaction can occur before a report. Checkpoint during work so recovery does not depend on predicting it.
4. On entry, after compaction, or when replacing the coordinator, fetch the remote. Read this page, the latest published CURRENT.md (including any open coordinator-record PR newer than main) and the preserved local coordinator worktree. Use git worktree list and compare local status, commits and CURRENT.md to the remote. A newer local pause or unfinished handover takes precedence over an older published snapshot. Verify the expected branch and revision; do not pull into a dirty checkout. Reconcile the roster, open PRs, their true merge state, review coverage, gate decisions and in-flight processes. Recover missing reports from the authorized chats or their task handovers. Mark uncertainty as pending. Follow the newest verified owner control before taking action.
5. Keep the requested dashboard in the coordinator chat on an approximately ten-minute cadence, showing the repository-wide open PR count separately from the original delivered queue. During pause it reports status only.

## Gate sequence, discovery and usage controls

Work gate by gate. Verify G(n) is natively blocked by G(n-1), plus applicable unresolved evidence gaps. Tasks depend on their real prerequisites and the preceding accepted gate; do not create a task-to-own-gate cycle. Read back native relationships, preserve owner-controlled acceptance and keep carried gaps in the earliest affected gate and G5 where required. Parallel independent work is allowed only inside the active eligible gate or explicitly authorized maintenance.

Worker assignment/checkpoints require active Graphify discovery scoped to MaexSocial: query, indexed commit/coverage, checkout SHA, discovered callers/files/tests and fallback reason. Same-revision complete results need no redundant search. Read unindexed plans/instructions and changed/local source directly; unavailable Graphify falls back honestly to local discovery. No private ledger/secret/fixture upload or paid rebuild authority is implied.

Read actual shared usage before admission and approximately every ten minutes while active. The standing threshold is 7% remaining: close new intake at or below it, finish admitted work only absent a newer full pause. Unknown readings hold intake. A direct stop at 5% was a full pause and overrides finishing existing work. Reset, new dashboard data and skill invocation alone do not resume it. Never purchase/reset credits without authorization. Actual account readings stay private.
