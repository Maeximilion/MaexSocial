# External access, administration and tenant security

**G2 decision proposal, 2026-11-05.** Maxi confirmed public customer registration/login, isolated customer dashboards, a separately authenticated Windows application on the owner's PC for managing customers, and a pilot with one local business and one approved Google Business Profile (GBP) text post. The role and invitation decisions below are confirmed. The remaining controls and numerical limits are G2 proposals. No account, service, client or staging assessment was exercised. ## Entry points and trust boundaries

`customer.domain` denotes the proposed customer origin. Real DNS, identity provider (IdP), host, region and costs need approval with #8. Route names below describe testable contracts, not deployed addresses.

```text
Customer browser --> HTTPS customer.domain --> customer API --> tenant records / audit
       |                    (public site, signup, login, customer-only dashboard)
       +--> system identity service --> verified customer session on customer.domain

Enrolled Windows PC --> system browser --> identity service (dedicated admin client + MFA)
       +--> private transport + device proof --> admin API --> customer directory / audit
                                                  |
                                      selected workspace state change

Customer approval --> tenant-bound intent --> private worker --> credential vault --> GBP
                           |                     |
                    tenant record store   scoped result/readback --> customer API
```

Public access ends at web/identity ingress. Customer API accepts only customer sessions. A private admin ingress accepts only enrolled devices over a mutually authenticated channel and a separate admin identity/session. Bind the session to that device key and verify proof on each call. Neither a cookie from the portal nor a public-client identifier is administrative authority. Only backend services may reach stores, queue, vault or audit sink. Only the scoped worker receives a usable provider credential for dispatch/readback. The PC has no database connection. Logical routes may share backend code, but each enforces its own audience, active principal, action and target even on raw HTTP calls.

## Permissions for the text pilot

The pilot has two customer roles, Employee and Manager. DEV/Admin uses a separately enrolled Windows identity to manage customer organizations. For every request, resolve the actor, active customer membership or platform grant, target and permitted operation on the server. Deny unlisted operations and caller-supplied privilege overrides. [Owner decision on roles and invitations](https://github.com/Maeximilion/MaexSocial/issues/30#issuecomment-6671733744) · [Owner decision on the per-occurrence hold](https://github.com/Maeximilion/MaexSocial/issues/30#issuecomment-6670980326) · [Owner clarification on approval and export](https://github.com/Maeximilion/MaexSocial/issues/30#issuecomment-6671746885)

| Resource / operation | Visitor or unverified | Employee | Manager | DEV/Admin | Service |
|---|---|---|---|---|---|
| Public site, signup, login and recovery | Public entry only | Own identity | Own identity | Separate admin entry | IdP handles identity only |
| Workspace facts, drafts and results | Deny | Read/edit own tenant drafts and read its results | Same, plus manage workspace settings | Deny content access | Worker reads exact approved revision |
| Approve a post | Deny | Deny | Own active tenant, exact revision, authorized location and occurrence | Deny | Worker may dispatch only that intent |
| Export approved text when required Google access is unavailable before dispatch | Deny | Exact Manager-approved revision in own active tenant | Same | Deny | Backend commits terminal export before releasing text |
| Create a customer organization or create/approve customer user access | Deny | Deny | Employee invitations only, as below | Select target organization, email and customer role (Employee or Manager) with fresh MFA and an audited reason | Audit targeted grant |
| Promote an active Employee to Manager, demote or revoke a Manager | Deny | Deny | Deny | Target customer and membership, fresh MFA and audit | Invalidate the changed grant immediately |
| Invite or remove an Employee | Deny | Deny | Own tenant only, Employee role only | May provision customer access as above | Recheck issuer and target on every mutation |
| Manage provider connection | Deny | Deny | Own tenant with verified account-owner grant | Deny | Backend stores grant reference and worker uses least scoped credential |
| Hold one occurrence | Deny | Deny | Own tenant may withdraw its approval | Target tenant + occurrence, fresh MFA and reason; minimal state only, no content or release/send authority | Serialize hold against dispatch claim; retain in-flight result |
| Customer directory, account status, suspend/reactivate | Deny | Deny | Own status only | List minimal identifiers/status; target one tenant per change, fresh MFA, reason and audit | Authorization service enforces invalidation |
| Audit | Deny | Own customer-visible results only | Own workspace event summaries | Management/security events only, scoped target on detail | Restricted append/read identities |
| Originals, thumbnails, derivatives, remote media, generation, schedules, ad accounts, spend | Deny | Disabled | Disabled | Disabled | Disabled; zero retrieval, processing or billing |

Never export raw audit logs or credentials. No platform impersonation, arbitrary customer downloads, platform-role delegation via UI or destructive deletion in the pilot. Future media roles must differentiate upload, preview/download, export, processing and spending. Every read/write of originals, thumbnails, derivatives, jobs, schedules or ad connections requires current workspace **and** operation authority; release those features only after their own design and relevant UPLOAD-01–10 evidence. ## Identity and endpoint controls

### Public registration and invited access

- **Public registration.** Keep self-registration and login available independently of invitations. Return the same public response for new, existing and pending emails. If the email belongs to a verified identity, send sign-in or recovery guidance only to the mailbox. Preserve the identity's credentials and memberships. Signup creates a pending identity. After proof of mailbox control, discard unverified credentials, authenticators and sessions before the owner sets initial credentials. Activate the intended new workspace and ordinary Employee membership exactly once. Ignore requested elevated roles. Email domain or address alone never joins an existing customer. Signup and recovery cannot grant Manager or DEV/Admin authority. The first Manager requires a separate admin action. On the enrolled PC, DEV/Admin selects the active verified Employee and target workspace, provides fresh phishing-resistant MFA and an audited reason, then directly changes that membership to Manager. Rotate the affected user's session on elevation and reject the old session. Until this grant commits, Manager operations stay unavailable. Reissuing or accepting an invitation cannot elevate an existing membership.
- **Issue an invitation.** DEV/Admin may create a customer organization and provision or approve access for a selected email, tenant and customer role. An active Manager may invite or remove only Employees of their own tenant. The server rejects cross-tenant changes, Manager creation or promotion through that path, and any platform-role request. Record the issuer, target customer, intended role, expiry and grant version. Require fresh MFA for grant changes. Email the invitee a purpose-bound, single-use link. Store only its token hash and propose a 24-hour lifetime. Resend invalidates the old link. Revocation cancels the pending grant.
- **Accept an invitation.** Display the target customer and role. Opening the link performs no mutation. On explicit confirmation, serialize acceptance with revocation, role changes and tenant suspension. In the same transaction validate the email binding, expiry, current issuer authority, grant version and active tenant, consume the token and create the intended membership. A new user sets their own password and supplies first and last name. Further profile fields are optional. If the invited email has an unverified signup, require the invitee to prove mailbox control, invalidate all credentials, authenticators, challenges and sessions from the pending signup, then let the invitee establish their own credentials. Complete these steps before the invited grant becomes active. An already verified user must sign in as the matching identity and confirm the membership, supplying any missing required names. Preserve existing credentials, profile, roles and memberships. A stale or competing invitation cannot replace an existing role or reactivate removed access.
- **Remove access.** A Manager can revoke only the target Employee membership of their customer. DEV/Admin may revoke a Manager's membership or change it to Employee with fresh MFA and an audited reason. Cancel affected invitations and invalidate authority derived from the old grant. Immediately recheck the affected user's tenant grant for sessions, queued work, private downloads and exports. Revocation applies even to the last Manager. Manager-only operations then stay unavailable until DEV/Admin provisions a replacement. Employees are never promoted automatically. A shared identity retains its other active memberships. Reinstatement needs a fresh authorized grant.
- **Verification and recovery.** Hash opaque challenges at rest. Bind to purpose and account. Use explicit, atomic confirmation so link prefetch or concurrent redemption cannot activate twice. Proposed expiry is 24 h for verification and 15 min for reset. Resend invalidates prior links. Reset revokes sessions. Neither verification nor recovery revives suspended access. Offer passkeys and propose fresh MFA for publication approval. [OWASP authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

### Session and client controls

- **Browser.** Use a maintained IdP and server-side opaque sessions. Rotate on login or privilege change; expire after 30 min idle / 8 h absolute. Use host-only Secure, HttpOnly, SameSite=Lax cookies; validate CSRF token and exact allowed origin for state-changing browser requests, including login-flow state/nonce and fixed return destinations. No mutation by GET. Keep tokens out of URLs except single-use links, whose pages suppress referrers, third-party loads and token logging. Reject plaintext credentials; redirect only safe navigation. [OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) · [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- **Abuse.** Generic responses with equivalent status, body and timing envelope for existing, absent, suspended and pending identities. Candidate limits per normalized account and independently per source: 5 attempts/account and 30/source per 15 min for login; 3/account and 10/source per hour for signup, recovery and resend per flow. Increment both counters even for unknown identities; test NAT/shared-source behavior, throttle without permanent account lockout. Never log submitted passwords, raw email challenges or token-bearing URLs.
- **Admin bootstrap.** Designate Maxi as owner of a restricted out-of-band provisioning procedure. Verify named operator and intended device out of band. Bind non-exportable device key to approved enrollment through one-time short-lived challenge and proof of possession. Pre-enroll two user-verifying hardware security keys, store spare separately, and require a fresh phishing-resistant assertion for each occurrence hold, customer creation, customer access grant or role change (including first-Manager promotion and revocation), customer suspension/reactivation or device change (max age 5 min). Signing/admin bootstrap credentials stay out of app bundles. Customer sessions, signup, password resets or email alone can never provision/recover a platform admin. [NIST authenticator lifecycle and phishing resistance](https://pages.nist.gov/800-63-4/sp800-63b.html)
- **PC sessions.** Public native client opens the system browser for authorization code with PKCE S256, exact registered redirect form (loopback with ephemeral port), state and nonce. Validate issuer, audience, expiry, MFA and device binding server-side. Keep access token in memory (5 min); prefer no persisted refresh token in the pilot. Any later persistent handle requires rotation, reuse detection and Windows current-user protection, never machine-wide or plaintext storage. Admin session idle 10 min / absolute 1 h. Clear local state on logout; server revocation overrides token lifetime. OS/user compromise can expose a running session. [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252) · [Windows data protection](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)
- **Distribution.** Recommend signed MSIX from an owner-controlled HTTPS release location. Install and update only trusted publisher packages; verify package identity, signature chain, integrity and allowed version before installation. Keep the signing key in restricted signing infrastructure, separate from admin and application keys. Reject unsigned, wrong-publisher, altered and downgraded packages. If compromised, stop distribution, revoke/replace signer and device credentials as affected, and suspend admin ingress pending clean re-enrollment. Client claims about its version or signature cannot authorize a request. A managed distribution channel is a viable alternative if its origin, update and rollback checks can be independently tested. [Microsoft MSIX signing](https://learn.microsoft.com/en-us/windows/msix/package/signing-package-overview)

## Threats and failure handling

| Attack or failure sequence | Enforcement and observable result | Cases |
|---|---|---|
| A swaps B's ID in query, nested write, cache key, list/search filter or export URL | Bind every lookup/mutation to active tenant + object + action, including composite references. Scope cache keys and reauthorize delivery; direct guess yields no B payload or effect. | ACCESS-02, 04, 06 |
| Malicious signup, portal token or modified desktop calls admin API directly | Reject wrong issuer/audience/device proof or inactive platform role. Record denial; allow only explicit directory/target actions. | ACCESS-01, 04, 05, 13 |
| Stolen PC, cookie, recovery link or old admin session | Owner can disable identity, device certificate/key and session family from an independent control plane. Reject next protected request after revocation commits, including refresh and existing connections. Fail closed if revocation state unavailable. Re-enroll on clean PC with spare key; both keys lost requires documented independent identity proof and bootstrap ceremony or service remains locked. | ACCESS-07, 08, 14 |
| Worker receives forged tenant, changed content or stale account grant | Load intent by server-held ID; join active tenant, subject, object, location, approval and credential version. Serialize suspension/stop with dispatch claim. Record in-flight boundary before external call. Never widen scope from queue fields. | ACCESS-02, 03, 07 |
| Lost provider reply, duplicate claim, suspension after accepted dispatch | Persist one intent per approved tenant/revision/location/occurrence, at most one create attempt. Confirm only on a uniquely correlated Google-side LIVE readback; ambiguous outcome remains unknown across restart, no blind retry. Hold later work; reconcile already in-flight privately. Reactivation requires fresh authority/approval before another dispatch. | ACCESS-03, 05, 06 |
| Forged browser writes, account enumeration, tampered update or leaked secret | Apply CSRF/origin, bounded auth flows, publisher verification and output allowlists. Exercise positive control after each denial; stop on any credential disclosure. | ACCESS-06, 08–11, 14 |

For a missing/denied/expired GBP grant **before dispatch**, an active Employee or Manager of that customer may export the exact Manager-approved text, privately, with “exported — provider result unconfirmed”. An edit invalidates approval. Recheck current tenant, membership, revision, location, occurrence and approval before releasing text, including repeat downloads. Serialize this check with edits, holds and revocation. Deny stale or withdrawn approval, a suspended tenant, removed membership or a different customer. Claim export and dispatch as mutually exclusive transitions on the same durable occurrence. Commit the terminal exported state before releasing any text for manual submission. An authorized repeat download returns the same revision; reconnecting a grant never reopens that occurrence. If dispatch wins the claim, the export path must withhold manual-submission output. No create or reported success on the exported path. If dispatch may already have occurred, display “outcome unknown”, reconcile first and prevent duplicate manual send. Never treat an export, API acceptance alone or a fake receipt as proof of publication. [Provider feasibility](research/platform-api-feasibility.md) · [#8 publication plan](https://github.com/Maeximilion/MaexSocial/issues/8)

## Data, recovery and rollback proposals

Use TLS for every network hop, encryption at rest for stores and backups, service-specific access and externally managed encryption keys. Candidate region is EU for primary, replicas, logs and backups; #8 must name the actual host/IdP/mail processors, provider transfers, region guarantees, cost and key custodian before acceptance. A region proposal does not establish a provider residency guarantee. Restrict key administration to named operations custodians. Separate decrypt rights by service and environment. Audit key use, rotation and backup restores.

| Data / purpose | Permitted readers | Candidate retention and deletion |
|---|---|---|
| Identity, verification and membership for access | IdP / authorization service; admin sees minimal identity and status | Active account lifetime, purge within 7 days of authorized deletion; expire challenges as above |
| Business facts, drafts, approvals and private exports | Authorized tenant, narrowly scoped backend/worker | Until deletion or account exit; purge online within 7 days. Generate exports on demand without public links |
| Provider grant, intent and receipt for one send | Vault/credential service and assigned worker; customer sees result projection only | Disable grant use on revocation, delete vault material within 24 h; retain minimized intent/receipt 90 days after resolution. Hold unknown intents for restricted reconciliation with named owner |
| Management/security audit for incident reconstruction | Restricted audit reviewer; approved tenant summaries only | 90 days online, append-only restricted sink, expiry job; document incident holds and review monthly |
| Media originals and derivatives | Nobody in text pilot | Disable inputs, storage and retrieval. Before enablement #43 must set limits, readers, processor regions and deletion/backup periods |
| Encrypted backups for recovery | Named restore operators only; separate backup key | Rolling 30 days, last recoverable copy expires within 30 days of online purge |

For each privileged action capture actor, device/session reference (non-secret), target, action, reason code, time, outcome and correlation ID. Couple an allowed management mutation to a durable audit event in the same transaction; if recording fails, deny the mutation. Record denials without copying customer content or raw identifiers into public evidence.

**Incident drill.** On lost PC immediately suspend admin ingress/identity from the independent recovery path, revoke device, sessions and affected keys, preserve minimal evidence, inspect targeted actions and notify the owner. Reconcile in-flight sends before reopening. Roll back only to a signed known-good client and compatible service/schema under an explicit recovery decision; keep ingress blocked for vulnerable builds. Restore backups into isolation, replay an independently retained deletion/revocation ledger covering the full backup horizon, rotate stale credentials, and verify tenant separation before reopening ingress or workers. Quarantine **all** pre-restore occurrences, including apparently unsent ones. A send or manual export may have committed after the snapshot. Reopen new work separately; release a historical intent only on independent, conclusive evidence that neither path claimed it. Keep ambiguous cases held even if readback finds no match. Never restore a revoked grant or replay a send as a restore side effect.

## Decisions for Maxi at G2

| Decision | Recommended pilot choice | Safe alternative / cost |
|---|---|---|
| Identity and device recovery | Managed IdP with distinct customer/admin registrations, revocable sessions, two admin hardware keys and independently accessible recovery plane | Maintained self-hosted IdP with the same contracts; assign patching, backup and recovery operator. Hold admin access if independent recovery cannot be verified |
| Admin reach and packaging | Private device-authenticated ingress, signed Windows MSIX, controlled distribution | Compare a privately installed web app on managed Windows: centralized updates reduce package maintenance, but origin compromise changes client code immediately. Require device-authenticated private ingress, separate admin origin/session, trusted release pipeline, rollback controls and loss drill before choosing it. Owner selects Windows/device and signing support/cost before rollout |
| Privacy and operating limits | EU candidate region, retention/deletion periods above, fresh MFA and expiry/throttle values as proposed | Select another documented region/processor, stricter retention or adjusted limits after measured usability/recovery tests. Name processors, key/recovery custodians and a deletion owner |
| Enablement | Text-only release; #43 separately decides disabled-media contract. Require #82 scoped staging evidence before external access | Defer the exposed surface until its negative controls and recovery drill pass |

The customer roles, invitations, Manager-only approval, Employee/Manager export and targeted DEV/Admin hold have owner decisions linked above. Maxi records **accept / revise / defer** for each remaining decision against the reviewed revision on #30. #8 incorporates the disposition into the global plan, #9 maps accepted cases, and #15 records a separate G2 decision. Documentation, reviews and foundation checks alone cannot approve the design.
