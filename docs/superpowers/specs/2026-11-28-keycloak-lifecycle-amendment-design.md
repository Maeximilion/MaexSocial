# Proposed G2 amendment · Manager authority across credential changes

**Owner decision requested, 28 November 2026.** Keep the existing Keycloak issuer. Select an application-managed lifecycle for **source-level feasibility only**. Assign one identity-platform owner to demonstrate exclusive control of customer credential changes and trustworthy completion of each recovery. The application owner would enforce the resulting authority at the Manager action. If either obligation lacks a supported contract or an explicitly owned, reviewable component, keep sensitive entries closed. This proposal closes only [drafting task #303](https://github.com/Maeximilion/MaexSocial/issues/303). The accepted G2 tag retains its original scope.

## What a Manager authorizes

A Manager invites or removes an Employee from their own tenant, or approves a specific revision of a post. The server binds a single-use step-up attempt to the configured issuer, immutable subject, customer client, customer session, tenant and membership version, current identity generation, requested action and exact target or content revision. Binding starts **before** redirect to Keycloak. The existing private verifier checks the expected subject, signed OIDC response and achieved ACR 2 under its fixed enrolled-OTP policy. The attempt starts the five-minute budget. At the action, after all lock waits, require a valid attempt with time remaining, an active session, current Manager grant, tenant and target versions, and the same active identity generation. Record acceptance and consume the attempt with the business mutation in one AppDB transaction. An approval carries the generation and grant/target versions through subsequent dispatch or export eligibility. A previously claimed external effect follows existing reconciliation. [Private verifier](../../../apps/web/src/server/oidc.ts) · [Session checks](../../../apps/web/src/server/session.ts) · [Accepted access requirements](../../17_ACCESS_SECURITY.md)

The factor event proves use of an enrolled factor under this policy. Continuity until authorization depends on **every effective change** being ordered through the lifecycle authority. A completed recovery additionally needs a durable, independently attributable outcome for the intended operation on this exact identity. A successful login, a fresh token or matching email cannot tell which recovery succeeded. ## Two ways to keep Keycloak

| Normal journey | Keycloak-native lifecycle | Constrained application-managed lifecycle (proposed) |
| --- | --- | --- |
| Enroll, replace or remove a factor, including account self-service | Keycloak owns credential storage and its configured required actions. A custom provider would need to bind the executed factor to an authoritative subject generation and cover every enabled mutation path. | The customer starts the change in the product. AppDB first closes sensitive access for the subject. Keycloak still collects secrets and performs enrollment. Independent self-service paths must be restricted or demonstrably participate in the same protocol. |
| Operator changes, required actions and account status | Keycloak administrators can change credentials or schedule actions. A native authority must also cover their effective changes and work already admitted. | A scoped identity operator requests the same transition. Direct administrative, automation, federation and emergency paths must be inventoried. Disable unused paths or cover them. A planned break-glass change requires a prior durable service-wide hold and reconciliation before reopening. |
| Password reset and replacement factor | Keycloak runs the reset and required actions. A native authority would have to attest the intended recovery's final outcome and exclude all earlier credential authority. | A one-use, purpose-bound recovery opens one attributed operation. Keycloak owns password entry and replacement-factor enrollment. A separate trusted completion source must attest the required postconditions for that operation. The customer resumes on the same subject and gets a new session. |
| Manager decision | A provider-side authority would need an ordering contract extending through the AppDB business commit, with defined failure handling. | AppDB orders each enrolled subject's changes and Manager mutations on the same lifecycle record. This works only if every provider change goes through the pre-change hold and has a conclusive terminal outcome. |

**Evidence boundary.** OIDC Core is a published protocol. Keycloak's versioned Admin REST reference documents credential administration and action delivery. Its developer guide describes installing providers built for the targeted Keycloak version. The inspected event listener lives in `server-spi-private` and documents callbacks in a running Keycloak transaction. These sources establish neither comprehensive pre-change mediation nor a transaction shared with AppDB. Internal source describes this build and carries no cross-version compatibility promise. Signed back-channel logout, timestamps, polling and asynchronous events can prompt revocation or investigation. None gives the application a complete ordering or a recovery attestation. The native option would add a privileged Java extension plus an inter-system protocol and compatibility review at every upgrade. No native candidate meeting this contract is established. ## Where authority changes

1. **Start the change.** After authenticating the change request through its approved channel, the application locks the issuer/subject record, advances a never-reused generation and commits a pending operation before releasing any provider-side work. A recovery revokes old application sessions and outstanding challenges, attempts and approvals derived from the old authority. The accepted recovery challenge remains purpose-bound, single-use, CSRF-protected and valid for 15 minutes. An unsolicited public reset request alone cannot lock a known account. Other credential changes may leave a customer session present for ordinary use under existing controls. A surviving session's old proof authorizes **zero** sensitive actions.
2. **Complete a bounded provider operation.** Store an opaque operation ID, intended type, identity, expected generation and phase before dispatch. Only an authenticated lifecycle executor may submit the provider operation. It must support an idempotent operation identity or conclusive status lookup for lost responses. Ordinary browser completion, event arrival, a request accepted for delivery or a list of credential IDs is insufficient. A trusted provider-side completion authority independent of the browser and request initiator must bind its terminal result to this operation, subject and generation. For recovery it must establish durable completion of the intended password change and replacement enrollment, usable new credentials, exclusion of old credentials, links, sessions and previously admitted changes that could still take effect. **This completion authority and exclusive mediation are prerequisites to be designed and evidenced.** The stock deployment supplies neither contract.
3. **Reopen access.** Check authenticated attribution and expected phase under the same lock. Only a matching terminal success can commit active status at the new generation. Recovery requires a new login and fresh enrolled-factor step-up bound to the new session and requested Manager action. An exact duplicate returns the recorded result. An older generation cannot overwrite a newer one. A contradiction about current authority holds the subject for operator reconciliation. Missing or ambiguous completion leaves access closed. No timeout or operator checkbox reactivates it.
4. **Order actions.** A sensitive action and a change contend on the same AppDB record through commit. If the change commits its hold first, any outstanding old attempt is denied. If the action commits first, its recorded result stands, then the change invalidates remaining authority and any unclaimed approval from the old generation. A change between the factor challenge and action commit follows the same rule. This argument assumes the provider cannot change first or complete older work afterward. It is a design obligation, not an observed Keycloak property.

```text
Active(g) -- verified change; AppDB commits hold --> Pending(g+1, operation)
Pending   -- response lost / restart ------------> Held(g+1, same operation)
Pending or Held -- correlated terminal success --> Active(g+1)
Pending or Held -- unknown / contradictory ------> stay closed for reconciliation
```

**Outages and restart.** Resume the durable operation after restart. Never issue a second uncorrelated mutation on timeout. Persist a terminal outcome and deduplication key before making completion visible. An unavailable AppDB cannot grant a sensitive action or initiate a change. If provider verification or required current-status checks are unavailable, deny. A verified customer sees “Recovery is being verified. Manager actions are unavailable.” They may revisit status or contact support through the existing trusted channel. Public responses preserve account-existence equivalence and throttles. A failed or ambiguous recovery can require manual investigation and extended loss of access.

**Operations and retention.** Keep the identity executor, customer web service and independent management client separate. The customer service cannot administer the realm, read factor secrets, impersonate a user or declare recovery complete. A named operator owns reconciliation and a named platform maintainer owns realm configuration, completion credentials and version compatibility. Retain the current generation for the identity's lifetime. Keep minimal tombstones for as long as earlier requests, callback retries or restorable backups could reappear. Define enforceable maximum lifetimes before pruning, including disaster recovery. Restore in isolation and replay independent revocations before reopening. Retain minimal restricted audit records under the existing proposed 90-day policy and encrypted backups for the proposed rolling 30 days. Record opaque references, actor, phase, time and outcome. Keep secret material and raw tokens out of logs. [Retention and recovery policy](../../17_ACCESS_SECURITY.md#data-recovery-and-rollback-proposals)

## Acceptance and ordered follow-up

These are acceptance examples for a later approved design. This document supplies source analysis only.

| Journey | Required evidence |
| --- | --- |
| Legitimate recovery, replacement factor and approval | One named recovery completes for the same issuer/subject. The customer keeps their profile and legitimate memberships, can sign in with the new credentials, enrolls or proves the required replacement factor and uses a new session to approve exactly the requested post revision in their own tenant. Prior authority stays excluded. |
| Ordinary enrollment change around an action | A pending hold prevents old proof from authorizing. A completed action is attributable to the generation active at commit. An unclaimed old approval requires reapproval, including after a later role restoration. |
| Lost answer, duplicate or out-of-order notice | Restart retains the hold and operation identity. An authenticated duplicate has one outcome, an older notice cannot reopen access and an ambiguous current result leaves the action unavailable. |
| Wrong or expired proof | A changed target, tenant, session, subject, membership or generation, an expired attempt or an already consumed attempt produces no Manager mutation. Positive controls for the legitimate customer must still succeed after proven completion. |

1. **Decision and coverage dossier.** If Maxi selects this direction, the identity owner maps every enabled write path in [the realm configuration](../../../ops/local/keycloak-realm.json) and the pinned provider sources. Identify a published contract or name the new component, its owner and its authority for *both* exclusive mediation and operation-specific completion, including older admitted work. Scope covers existing and newly enrolled subjects, admin emergency changes, reloads and upgrades. Stop if any path can change authority outside the hold, or if completion cannot be independently attributed. The alternative is to retain the current G2 contract, keep both entries closed and reconsider only on specific new evidence.
2. **Contract and operational sign-off.** With coverage in hand, specify minimal rights, authenticated completion schema, retry/reconciliation semantics, privacy bounds, retention and restore prerequisites in [the identity evidence record](../../security/identity-generation-evidence.md) and [access policy](../../17_ACCESS_SECURITY.md). Operations must accept the self-service restrictions, recovery support burden and per-version requalification. An unowned path, indefinite retry horizon without safe retention, or unproven restore behavior ends this phase.
3. **Separate implementation decision.** Return the contract and cost to Maxi for explicit approval of the actual G2 amendment and check applicable gates. Only then could a separately authorized private slice target the [OIDC verifier](../../../apps/web/src/server/oidc.ts), [session guard](../../../apps/web/src/server/session.ts), [domain contracts](../../../packages/contracts/pilot.ts) and AppDB migrations. Require approved positive/denial evidence against the acceptance table before considering either customer entry. The excluded experiment remains outside the plan. No implementation, deployment or external spending is admitted here.

The choice today is whether to fund the design effort in **owner time**: one coverage dossier, one review with operations, and a compatibility decision for every Keycloak upgrade. No support subscription or new service is assumed. Failure to prove the contract leaves ordinary recovery support constrained and the two Manager entries unavailable.
