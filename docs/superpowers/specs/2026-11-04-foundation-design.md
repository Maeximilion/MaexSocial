# MaexSocial foundation design

## Authorization and intent

On 2026-11-04 Maxi requested the GitHub repository, Project, milestones, tags, tasks, PR/issue maintenance, workflows, documentation and agent instructions modeled on Maex-Voice-Agent. He also requested separate Codex and Claude Code REA investigations, their synthesis in a new chat and implementation after planning. This design covers the authorized foundation and research preparation.

## Chosen approach

Adapt the reference's numbered documentation, work packages, gate milestones, agent playbooks and visual README conventions. Create a lean foundation whose checks validate the repository that exists. A wholesale copy would carry restaurant-specific code and obsolete local policies. A bare repository would omit the requested collaboration infrastructure. The adapted foundation is the implementation approach chosen under Maxi's instruction to determine the steps.

## Deliverables

- Public `Maeximilion/MaexSocial` repository and one linked GitHub Project, number 5.
- Root README, agent rules, contribution/security/license files and original visual assets.
- Numbered project documents, stable MS task IDs and G0–G5 criteria.
- Issue/PR templates, labels, milestones, Project fields/iteration and initial issues.
- Foundation validation, PR metadata checks, dependency update configuration and documented Project synchronization.
- Independent REA briefs and synthesis/build handovers.

## Global constraints

- Product name is MaexSocial and repository is Maeximilion/MaexSocial.
- Repository content is public and research artifacts must be sanitized.
- Application stack and paid providers remain undecided until G2.
- Code-autopilot and caveman remain disabled.
- Code reviews use gpt-6-astra with reasoning high, verified in the actual session.
- Product implementation follows research synthesis and explicit G2 design approval.
- Project automation remains disabled until its dedicated credential is configured and verified.

## Sources of truth

The charter defines gates. Status records current state and decisions. Work packages define dependencies and acceptance. Research reports substantiate capability claims. GitHub issues and the Project expose delivery progress. All cross-references use stable task IDs and actual URLs.

## Verification

Check repository files and local links, workflow syntax and minimal permission declarations. Verify remote visibility/default branch, labels, milestones, issues, Project membership and field configuration. Run checks on the actual pushed commit. Distinguish configured workflows from successfully executed ones and missing credentials from working automation. Follow the current root rules for review and merge.

## Later design

G1 reconciles public claims, static observations and runtime evidence. G2 decides first customer/channel, application stack, account authority, cost envelope, retention and implementation plan. These are product decisions, so the foundation must not imply they have already been approved.
