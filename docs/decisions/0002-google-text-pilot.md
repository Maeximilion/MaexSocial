# ADR 0002 — Deliver one customer-approved Google text post

**Proposed · 2026-11-05 · decision owner: Maxi ([MS-008](https://github.com/Maeximilion/MaexSocial/issues/8)).** Package B recommends one modular TypeScript application and a separate worker from the same release, backed by one PostgreSQL transaction boundary. Choose it if a named operator can maintain the identity service, database and recovery procedure below. Otherwise revisit managed hosting before accepting the design. Implementation, provisioning, spending and live publication require separate decisions. [ADR 0001](0001-application-language.md) · [G2 work plan](../superpowers/plans/2026-11-05-g2-work-plan.md)

### Which system owns a send after a crash?

The planning case is one local business, one location and one approved organic text revision. Google accepts the write, the reply is lost, and the operator restarts the service. All three alternatives must preserve the same occurrence and prevent another create. [Pilot decision](https://github.com/Maeximilion/MaexSocial/issues/8#issuecomment-6662099692)

| Approach | Who enforces the hold, and what survives restart? | Operating consequence |
|---|---|---|
| Modular service + worker (proposed) | The worker claims the approved occurrence in the same store as a customer withdrawal or admin hold. After an ambiguous send it reads the original attempt and reconciles. | One release and data model to restore. The team owns migrations, alerts for unresolved attempts and worker recovery. |
| Workflow-led | An engine can expose a timeline and manual recovery. Its send step still needs a durable claim shared with the approval store and a resume path that only reconciles. Step replay after timeout could duplicate the post. | Extra privileged execution history, credential controls and engine upgrades. Reconsider if an existing supported engine proves the stop race and replay tests at lower operating effort. |
| Hybrid | Keep the application as sole owner of the claim, hold and provider write. A workflow can wake the worker repeatedly using the occurrence ID, without a provider credential. | Wakes can be deduplicated, but two systems need monitoring. Reconsider for measured, separately authorized media processing. A single text post gives the second system no job. |

```text
Customer browser -- verified, opaque session --> public customer API -- membership + role --> tenant approval
Enrolled PC -- system browser / admin OIDC + PKCE --> memory-only admin token
           -- private device-authenticated channel --> admin API -- target + fresh MFA --> audited hold
Customer API / admin API -- scoped DB roles --> PostgreSQL (revision, occurrence, intent, audit)
Worker -- atomic dispatch claim --> PostgreSQL; worker -- restricted grant from vault --> GBP create
Worker -- authorized, account-bound readback --> customer result via customer API
Lost PC --> independent recovery operator --> revoke device, identity and sessions --> deny next protected call
```

The PC and browser have no provider grant or DB access. Bind the admin session to an enrolled non-exportable device key; validate proof on each request. For a hold, require fresh MFA, reason, tenant and single occurrence. Commit the audit event and hold together or deny the change. Admin cannot approve, release or publish customer content. Revocation applies to existing connections too. Restore access on a clean PC using independently verified recovery and the spare authenticator. [Owner decision on #30](https://github.com/Maeximilion/MaexSocial/issues/30#issuecomment-6670980326) · [Access design and fixtures](../17_ACCESS_SECURITY.md)

### Dispatch and reconciliation contract

1. The customer approver authorizes the exact revision, account/location, due time and occurrence. Make the occurrence ID stable across revision edits and duplicate submissions. Store approval separately; an edit invalidates it. Project approval, a manually signed-in authorized account owner, eligible location, current grant and a policy-permitted project model are all prerequisites. Keep the worker internal. Withhold live dispatch while any prerequisite is unknown. [GBP access](https://developers.google.com/my-business/content/faq) · [Usage policies](https://developers.google.com/my-business/content/policies)
2. Serialize hold, export and dispatch on that occurrence. In one transaction validate the current approval, membership, policy, grant, tenant, due time and spend authority, then persist an in-flight attempt **before** the external call. A committed hold wins against a later claim. A later hold reports the original in-flight result. If required access is unavailable before claim, an authorized customer can atomically claim terminal export before receiving the exact text. A restored grant cannot revive an exported occurrence.
3. Permit one outbound create for the claimed attempt. Disable automatic HTTP/proxy retries of the POST. A crash after commit but before sending can therefore lose a send; preserve uncertainty instead of risking a duplicate. Across timeout, crash or incomplete receipt, withhold manual export and further creates. Reconcile with bounded read-only checks within granted quota. Use the original resource on the authorized location where available. Without a uniquely verifiable match, escalate to the named operator; similar text or timing alone cannot establish identity. Customer sees pending, rejected, confirmed or unknown. Only an independently correlated Google-side LIVE result counts. [Google create](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.localPosts/create) · [Resource states](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.localPosts)
4. Keep our intent, consent, audit and resolution facts separately from Google-returned content. Read Google data on demand; keep it out of long-lived logs and backups. Any performance cache requires specific policy review, restricted access and expiry within 30 calendar days, including after restore. Permission to retain a provider identifier for reconciliation must be established before relying on it. If evidence expires without correlation, keep our unresolved state. [Storage policy](https://developers.google.com/my-business/content/policies#content_storage) · [Retention proposals](../17_ACCESS_SECURITY.md)

### What would one pilot month cost?

**Planning scenario, USD before tax, public list prices checked 2026-11-05.** One full month in Frankfurt, one customer, one approved text post, one administrator. An 8 GB single-host Linux/IPv4 bundle is a sizing assumption. Model at most 1 GB of encrypted logical backups across the retention window, under 25 GB bucket transfer, low portal traffic within the VM allowance and at most 100 small verification/recovery emails. Confirm actual load, German-region pricing, processor terms and account eligibility before purchasing.

| Cost component | Units and planning amount |
|---|---|
| Host and primary disk | 1 × USD 44/month, 2 vCPU, 8 GB RAM, 160 GB SSD, 5 TB transfer. Capacity and restore time require a staging measurement. [AWS bundle table](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-bundles.html) |
| Off-host encrypted backups | 1 × USD 1/month including 5 GB and 25 GB transfer. Crossing 5 GB moves the estimate to USD 3 for the 100 GB bundle if deliberately selected; otherwise regional overage applies. [AWS object storage pricing](https://aws.amazon.com/lightsail/pricing/) |
| Keys, vault and mail | Illustrative two customer-managed KMS keys at USD 1/key-month, up to five secrets at about USD 0.40/secret-month, plus request charges. At up to 100 emails, basic outbound mail is under USD 0.02 at the cited à la carte rate before data/options. Verify the account's actual plan. [KMS](https://aws.amazon.com/kms/pricing/) · [Secrets Manager](https://aws.amazon.com/secrets-manager/pricing/) · [SES](https://aws.amazon.com/ses/pricing/) |
| Organic Google publication | Google lists its API at no charge for registered users. Actual LocalPosts quota/access is unknown. A zero quota requires access approval. No ad account, paid generation or paid distribution is in the pilot. [Google API pricing](https://developers.google.com/my-business/content/pricing) · [Quota limits](https://developers.google.com/my-business/content/limits) |

Host and backup subtotal **USD 45/month**; roughly **USD 49/month for the listed baseline** before variable charges. Adding a second identical host adds USD 44/month before any replication or failover work. Neither figure caps a bill. Domain/DNS, signing certificate or signing service, hardware keys, key/request volume, logging, transfer overages, restore environments, tax, support and operator time are outside the subtotal; the all-in total is unknown. Verify mail, signing and backup custody independently. A quote, payer, operations owner, billing alerts and explicit absolute limit per currency and period are needed before provisioning. Alerts alone cannot enforce a limit. Keep generation/ad connectors disabled. Any later billable job must reserve against tenant authority atomically before dispatch, settle once and retain uncertain reservations for reconciliation.

Decide processor/region and key custody, admin recovery, retention/deletion bounds, payer and authorized ceiling separately. Record the decision on the reviewed revision. **Acceptance inputs for [MS-009](https://github.com/Maeximilion/MaexSocial/issues/9).** Run these against a deterministic fake and synthetic tenants first; customer/provider-side G3 evidence requires separate authorization.

| Input | Required observation |
|---|---|
| Duplicate approval, concurrent workers, revision changed or membership revoked before claim | At most one create for a valid approval; zero creates for stale authority. No cross-tenant effects. |
| Race admin hold vs claim on A1; repeat with failed audit or stale MFA and another eligible A2 | Hold first: zero creates on A1, A2 unaffected. Claim first: retain outcome for reconciliation. Invalid hold cannot mutate or authorize a send. |
| Pre-dispatch access missing, export races claim; restore grant | Export wins: exact approved text, zero creates forever on this occurrence. Dispatch wins: no manual export; reconcile that attempt. |
| Fake accepts then drops reply, worker restarts; repeat crash between claim and send | One create in the first case, zero in the second; no reissue in either. Confirm only uniquely correlated LIVE readback; ambiguous match remains unknown. |
| Lost PC, wrong audience, cross-tenant ID or downgraded/tampered MSIX | Deny protected access or installation; revoke pending sessions/device, verify spare-key recovery and legitimate customer control. Map all [ACCESS fixtures](../17_ACCESS_SECURITY.md). |
| Two jobs each request four synthetic units with five available; repeated settlement | At most one reservation, one settlement. Unknown charge remains reserved; real paid paths stay disabled. |
| Restore a pre-dispatch backup after a later possible write, revocation or purge | Disable dispatch before restore. Reconcile against separately preserved post-backup dispatch, revocation and deletion evidence before reopening. If evidence is incomplete, suppress affected sends, grants and deleted records; require operator disposition. Verify restore time/data loss against the owner targets. |

Keep uploads and media retrieval disabled for this text path. [#88](https://github.com/Maeximilion/MaexSocial/issues/88) blocks [G5](https://github.com/Maeximilion/MaexSocial/issues/18); verify any gap needed by the pilot before relying on it.
