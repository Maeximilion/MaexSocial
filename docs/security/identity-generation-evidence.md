# Identity generation evidence for MFA

Source-only disposition for [#149](https://github.com/Maeximilion/MaexSocial/issues/149), 2026-11-17. **No complete supported generation contract was established in the inspected sources.** This is a bounded negative/unknown result, not proof that Keycloak cannot support an adequate design. The private factor receipt must not yet produce application-session MFA authority or enable #123's Manager actions. #131, the affected #123/#124 Manager actions, integrated Task 2 and G3/G5 remain blocked.

**Reading the claims.** The RP can request active reauthentication with OIDC `max_age=0` and request the required ACR. It must verify the signed response, expected issuer, subject, audience, nonce and achieved ACR. OIDC `auth_time` dates the user authentication and `iat` dates issuance. Neither dates the individual factor. Keycloak's [ACR mapper](https://github.com/keycloak/keycloak/blob/e514445f9dcdabc5bdcf67cab56c1e49655de067/services/src/main/java/org/keycloak/protocol/oidc/mappers/AcrProtocolMapper.java#L105-L129) maps the achieved level, and its [AMR mapper](https://github.com/keycloak/keycloak/blob/e514445f9dcdabc5bdcf67cab56c1e49655de067/services/src/main/java/org/keycloak/protocol/oidc/mappers/AmrProtocolMapper.java#L99-L112) maps completed executions to method names. The time bound in the private receipt derives from the fixed flow and the original attempt. Adding RP reauthentication supplies no enrollment generation. [OpenID Connect Core §§2, 3.1.2.1](https://openid.net/specs/openid-connect-core-1_0-final.html#AuthRequest)

**What reaches the RP.** A validated signed back-channel logout token asks the RP to end sessions identified by issuer and subject, session ID (`sid`), or both. Its event denotes logout. Delivery may be retried after failure. Even a genuine received token establishes neither the cause nor a positive recovery outcome. Silence cannot establish that every effective change was delivered before the Manager action. Internal user/admin events and the [experimental Shared Signals credential-change signal](https://github.com/keycloak/keycloak/blob/e514445f9dcdabc5bdcf67cab56c1e49655de067/docs/documentation/release_notes/topics/26_8_0.adoc#L67-L72) describe changes. The [transaction analysis below](#time-commit-and-authority) and the [CAEP credential-change definition](https://openid.net/specs/openid-caep-1_0-final.html#section-3.3) provide no end-to-end ordering with AppDB. [OpenID Back-Channel Logout §§2.4–2.7](https://openid.net/specs/openid-connect-backchannel-1_0-final.html#LogoutToken)

**Decision boundary.** A change can take effect after factor verification, before session binding, or between the final status read and action authorization. #131 needs a supported authority that binds the event to the same identity across those boundaries and distinguishes completed recovery from an ordinary change. Pending, delayed or unavailable evidence requires denial. A later functioning login alone leaves the exclusion of prior authority unresolved.

## Question and scope

For the same configured issuer and immutable subject, what authoritative observation proves that a #143 factor event belongs to the current enrollment/recovery generation both when bound to an application session and when a later Manager action is authorized? The observation must account for relevant changes during step-up, after its return, and operations already in progress. A fresh event alone does not establish the answer.

This report implements the bounded source plan: inspect the merged interfaces; trace the selected version's metadata, mutation entry paths and event/transaction semantics; state supported guarantees and remaining unknowns; deliver documentation and one next decision. No overall architecture, new parser, API, plugin or prototype is proposed. The excluded private credential/provider-lock experiment was not read, reconstructed, executed or delegated. No provider runtime, credential, lifecycle, customer-data or configuration operation was performed.

## Time, commit and authority

[EventBuilder][events] defaults successful events to the current transaction and errors to a separate immediate transaction; its override can change that choice. The builder stamps the event before persistence/commit. [AdminEventBuilder][admin-builder] similarly stamps and sends in its current context. Both catch listener exceptions; the source does not promise that an arbitrary failed listener notification blocks the originating action. [DefaultKeycloakTransactionManager][transactions] processes after-completion transactions only after the main transactions succeed, and rolls them back after main failure. These are **source inferences within those implementations**; the [listener Javadoc][listener] supplies the narrower documented transaction contract.

For inspected local JPA writes, durable database effects depend on the encompassing transaction's successful commit; a method return, event construction or flush alone is not that completion. This does not determine external-storage visibility, global order between concurrent transactions, or when an AppDB consumer has observed every relevant change. An after-completion notification can be later than the provider commit. A pre-commit timestamp can precede another transaction's timestamp while its commit occurs later. These ordering possibilities explain why timestamp polling is insufficient; they are reasoning from source, not runtime observations or instructions for an experiment.

The missing contract must define an authorization point and preserve the accepted immediate-denial boundary. Merely comparing an epoch in two independent reads, even if one were available, would still leave ordering unspecified:

| Interval | Required guarantee, currently unestablished |
| --- | --- |
| During step-up | The provider attests which enrollment/recovery generation the actual factor event belongs to. A later “current generation” read cannot retroactively label an earlier event. |
| Return to App session binding | Admission binds the verified event and same issuer/subject to still-valid provider authority. A mutation effective between observation and local commit must not leave silently valid stale MFA. |
| Session binding to Manager action | At the defined action-authorization boundary, effective invalidation must be reflected and stale evidence denied. Local locks and a fresh status read alone do not prove this across two systems. |
| Already-started provider operation | The contract must account for when it can still become effective and how that affects accepted evidence and recovery postconditions. A currently empty event query does not establish that all earlier work has finished. This remains a source-contract question; the excluded experiment stays excluded. |
| Missing, delayed, conflicting or unavailable evidence | Deny the sensitive authorization; do not infer current authority from silence, elapsed time or a local version. Denial alone does not satisfy successful recovery's positive credential/availability postcondition. |

## Missing assurance and one next action

The missing assurance is **a supported, authoritative issuer/subject lifecycle state (or equivalent validity assertion), bound to the actual factor event, covering every relevant effective enrollment/recovery/admin change, with defined commit/visibility and action-authorization ordering**. It must distinguish pending/uncertain work, prevent stale authority after effective invalidation, and preserve #131's identity/credential recovery postconditions. This is a requirement, not an invented endpoint or a claim that an exposed version number alone would suffice.

**A complete AppDB-only delivery is not supported by this evidence.** AppDB can enforce its own versions, receipt consumption and session revocation. Unless every relevant provider change is proven to participate in the necessary authority ordering, those mechanisms postpone the missing provider guarantee. More local tables, hashes or a claim parser would not complete #123's prerequisite.

**One smallest next action for Root:** record this exact missing-assurance checklist and the blocked #123/#124 Manager actions in #131, then hold bridge implementation until new primary evidence arrives. Reopening requires a version-specific official contract or written provider determination identifying complete relevant mutation coverage, binding to the actual factor event, and effective invalidation through the action-authorization boundary. That new evidence must identify the supported version/configuration, observable assertion, mutation-path coverage and effective ordering, or explicitly state the remaining unsupported scope. Do not assign a second identical source-search task. This report prepares the bounded question for any separately authorized documentation/support exchange; it sends no external message and authorizes no experiment, extension, deployment, new rights or alternative architecture. Without satisfactory evidence, leave the bridge and dependent Manager actions unavailable and the blockers open. A new concrete source or provider answer, rather than another generic parser search, would justify reopening the investigation.
