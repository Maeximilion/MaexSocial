# Upload and media-processing security

Status: proposed G2 contract, [MS-014 / #43](https://github.com/Maeximilion/MaexSocial/issues/43). No customer upload endpoint, media worker or production storage exists yet. Repository artwork validation is implemented separately and does not establish service security.

## Threat model and default

An uploaded SVG can contain active browser content. Restricted image embedding differs from direct document navigation or `object`/`iframe` embedding; parser flaws and resource exhaustion create separate processing risks. The impact depends on origin, credentials and process isolation, not the filename alone. [MDN SVG image contexts](https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/SVG_as_an_image)

The [owner-confirmed pilot](https://github.com/Maeximilion/MaexSocial/issues/8#issuecomment-6662099692) covers one local business and one approved Google Business Profile text post. **Its media allowlist is empty.** Reject media fields and attachments at the API, including URL or object references on a draft, export or publication intent. Provision no customer media storage, upload grants, fetchers, processing jobs or paid media calls. Use the text workflow as the positive control.

If Maxi later authorizes a customer image trial, propose single-frame JPEG only. Reject SVG/SVGZ, other active documents, video, animations, ambiguous/trailing payloads and disguised content. Require matching declared type, signature, bounded full decode and a freshly encoded derivative. Apply the same boundary to replacements. [OWASP upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

## Required processing contract

1. **Authorize and quarantine.** Check tenant, upload authority and quota before accepting bytes. Store originals privately under generated keys; filenames and metadata are untrusted data. Quarantined content cannot be previewed, publicly retrieved, sent to a provider or used in a paid job.
2. **Bound actual decoding.** Fix encoded/decoded byte, pixel/dimension, duration/frame, concurrency, memory and time limits. Choose maintained decoders, validate signatures and decoded content, and reject unsupported, ambiguous or malformed files. Scanning can supplement these checks, not replace them. Treat derived/provider media as untrusted at the same boundary.
3. **Isolate processing.** A restricted worker receives only the intended object and output destination. No application session, admin/database/provider credential, privileged filesystem or unrestricted network access. Rasterization/transcoding is itself an attack surface. G2 must choose the concrete sandbox, egress policy and patching process.
4. **Promote verified outputs.** Publish previews only from allowed, successfully validated derivatives. Define metadata stripping and provenance. Apply tenant checks to originals, thumbnails, derivatives, jobs and replacements. Handle partial processing, quota reservation, deletion, retention and dependent scheduled content explicitly.
5. **Deliver safely.** Never inline arbitrary original documents on the authenticated application origin. For allowed original downloads specify exact content type, attachment disposition and `X-Content-Type-Options: nosniff`. Use a media origin without application cookies where appropriate, while retaining private access control. Define signed-link scope, expiry and revocation bounds; a public URL is not tenant authorization.
6. **Constrain retrieval.** If URL ingestion is enabled, allow only selected schemes/destinations, enforce time/byte/redirect limits and block private, loopback, link-local and metadata addresses across DNS resolution and redirects. Apply this to provider outputs too. Do not let a model choose unrestricted fetch destinations.

Audit acceptance, rejection, promotion, access and deletion without recording secrets or raw private content. A platform administrator needs separate explicit authority and a target-customer audit trail; uploading never authorizes publishing or spending.

## Proposed limits for a later JPEG trial

These are candidate ceilings for tiny pilot volume, not measured capacity or provider limits. MiB means 1,048,576 bytes. All limits apply together.

| Boundary | Candidate rule and reason |
|---|---|
| Input | One image per request, ≤8 MiB streamed within 30 s total. Enforce actual bytes even without Content-Length. Width and height each ≤4,096, total ≤12,000,000 pixels, one frame, zero video duration. A normalized four-byte pixel buffer fits within 48,000,000 bytes. Reject before oversized allocation and enforce limits throughout decoding. |
| Output and worker | One metadata-free JPEG derivative ≤2,048 px per side and ≤4 MiB. Cap the whole job at 256 MiB memory, 32 MiB scratch, one CPU core and 10 s wall time including re-encode. Kill the whole job on breach. Buffer, decoder overhead and scratch are separate limits. |
| Admission | One active ingestion per tenant, two service-wide across all instances, from reservation until terminal cleanup. Reject excess before body storage, with no waiting queue. Reserve up to 12 MiB for input + derivative atomically within a 128 MiB per-tenant stored-object ceiling. Count quarantine, partial writes and reservations exactly once; charge surviving bytes until removed. |
| Retry | One retry only for a transient worker crash, within the same reservation and asset version. Never retry malformed input or exhausted resource limits. Fence late attempts and publish a derivative once, only if its version and grant are still current. Reap abandoned reservations and partial writes within 1 h of failure or lease expiry. |

Run each decode in a disposable non-root sandbox with no network interface to external services, a read-only root, no host mounts and only a read-only input and size-limited output volume. A separately authorized broker stages one object and verifies output type, size and version before atomic promotion. Pin a maintained decoder and sandbox image by digest. Assign a patch owner and disable ingestion on loss of isolation or a known exploitable decoder issue until a patched candidate passes the hostile fixtures.

## Proposed access, delivery and deletion

- **Authority.** Check current tenant membership and the specific operation on every request and again on job claim/promotion. Separate upload/replace, preview, delete and external-use grants. Give the platform administrator no media-content access. The customer grants and any future exceptional admin action require a decision under [MS-013](https://github.com/Maeximilion/MaexSocial/issues/30).
- **Delivery.** Originals stay private and have no customer download route in the trial. Deliver only the derivative from a separate origin with no application cookies. Use an authenticated media gateway with a subject-, tenant-, object-version- and action-bound ticket valid for at most 60 s. Require proof of the same active user independent of the ticket. Recheck authority and deletion on each request, deny on lookup failure, and expose no direct storage URL. Use exact image/jpeg, nosniff and private, no-store responses. Check access on every range/repeated request. Revocation denies the next request after commit; bytes already delivered cannot be recalled.
- **Lifecycle.** Exclude originals, quarantine and scratch from backups. Purge originals after promotion and all remaining quarantine within 24 h of receipt. Retain a verified derivative until customer deletion, account closure or 90 days after promotion, whichever comes first. At that cutoff deny new reads/claims immediately, invalidate tickets and hold dependent scheduled work for explicit reapproval. Prevent in-flight or restored jobs from resurrecting deleted versions. Purge all online versions within 24 h. Keep rolling encrypted derivative backups for ≤30 days after online purge. Before releasing any restore, replay an independent deletion/revocation ledger covering that horizon and test that deleted assets stay inaccessible.
- **Audit.** Keep minimal actor, tenant, asset/version, action, outcome/reason code and time for 90 days, restricted to the designated audit reader. Exclude filenames, image metadata, URLs/tickets and payloads. A named deletion owner verifies purge and restore evidence. Region, processor, custodian, capacity, actual purge guarantees and incident holds remain unknown pending #8/#30 decisions.
- **URL and provider inputs.** Allow zero destinations, redirects and remote bytes in both text and JPEG phases. If G4 requests a provider output, first approve exact HTTPS host/path/port and a dedicated fetch broker. Proposed image-only fetch caps: 8 MiB actual decompressed body, 10 s total and zero redirects. Reject userinfo, non-public IPv4/IPv6 (including mapped forms), mixed DNS answers and IP literals. Pin a validated address for the connection while verifying TLS for the approved hostname. Enforce destination restrictions at egress as well. Never forward application credentials. Quarantine the result like an upload. Video needs separate codec, duration, frame and resource tests before any nonzero allowance. [OWASP SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)

## Proposed acceptance cases — not executed against an application

| ID | Input or sequence | Required result |
|---|---|---|
| UPLOAD-01 | SVG/SVGZ, SVG renamed PNG, false MIME, HTML/polyglot or unsupported content | Reject before preview, provider handoff or paid processing |
| UPLOAD-02 | Malformed file, excessive dimensions/duration, decode bomb or concurrent quota exhaustion | Bounded rejection, resource limits enforced, no worker/app outage |
| UPLOAD-03 | Quarantined original requested through direct URL, preview, job API or provider handoff | No retrieval, promotion or external processing before validation |
| UPLOAD-04 | Tenant A changes B's original/thumbnail/derivative/job ID, upload key or replacement target | No cross-tenant disclosure or mutation; authorized same-tenant control case passes |
| UPLOAD-05 | Traversal/control characters in filenames, metadata or storage key input | Generated safe keys; no path escape, response-header injection or executable metadata |
| UPLOAD-06 | Direct navigation, image, iframe/object preview and allowed original download | No active original on application origin; intended private access, MIME, attachment and nosniff behavior verified |
| UPLOAD-07 | Decoder tries to read app secrets, write outside its output scope or contact disallowed networks | Runtime restrictions deny access; per-job authority and resource limits verified in staging |
| UPLOAD-08 | URL redirects/DNS changes to loopback, private, link-local or metadata endpoint; oversized provider output | Retrieval blocked or bounded, including each redirect; no credential leakage |
| UPLOAD-09 | Reuse an expired/revoked signed link, delete an asset with derivatives and scheduled use | Accepted revocation/retention bounds enforced across all objects; dependent jobs cannot use unauthorized content |
| UPLOAD-10 | Duplicate job, processor crash or rejected derivative followed by retry | No premature promotion/paid handoff; visible failure, bounded retry and quota reservation recovery |

## Current repository artwork boundary

`scripts/svg_policy.py` checks the narrow inert SVG subset used by original brand artwork through `scripts/check_repo.py` and required foundation CI. Hostile fixtures are parsed, never rendered. `.svgz` is unsupported. The policy is not a general-purpose sanitizer and must never be reused as customer upload approval. A PR can change both artwork and its checker, so review remains necessary. See the implementation and regression tests for exact limits and accepted elements.

The 2026-11-05 baseline audit found no active content in the five existing SVG assets and no deployed upload path to test. It found the missing artwork check by passing an `onload` fixture through the old checker. No offensive remote test, full Git-history secret scan or production penetration test was performed.
